## 📑 1. MoSCoW 범위 선정 프롬프트

```markdown
우리의 앱 프로젝트(1인 가구 냉장고 케어 & 레시피 추천)의 핵심 목적 달성 여부를 기준으로 10~14주차 개발 우선순위를 4가지 범주로 분류해 줘.

1. Must have (필수): 빠지면 핵심 목적(유통기한 추적 ➔ 레시피 소진 ➔ 재구매)을 달성할 수 없는 기능
2. Should have (중요): 중요하지만 임시 대안으로 핵심 흐름 유지가 가능한 기능
3. Could have (여유 시): 핵심 흐름 완성 후 시간이 남을 때 추가할 기능
4. Won’t have this time (이번 제외): 1인 개발 5주 기한을 초과하여 이번 학기에서 제외할 기능

[현재 프로젝트 정보]
- 프론트엔드: Flutter (Dart)
- 백엔드/DB: Node.js (Express) + MariaDB (AWS Lightsail)
- 주요 기능 후보: 식재료 CRUD, D-Day 계산/정렬, 푸시 알림, 레시피 API 연동, 냉장/냉동/실온 탭, 소진 후 재구매 링크, 영수증 OCR, 소셜 로그인, 식비 절약 리포트

위 기준에 맞게 각 기능의 판정 근거와 함께 MoSCoW 분류표를 작성해 줘.
```

## 🧩 2. KISS · YAGNI 검토 프롬프트

```markdown
[KISS & YAGNI 검토 요청]

1인 개발자 5주 구현(30~50시간) 제약 내에서 15주차 발표 시연을 안정적으로 마치기 위한 KISS(유지할 조건) 및 YAGNI(보류할 예) 검토서를 작성해 줘.

1. KISS (Keep It Simple, Stupid) - 유지할 조건:
   - 핵심 기능: 식재료 등록 시 이름, 보관장소, 유통기한만 탭하는 3초 입력 폼 구조
   - 레시피 매칭: 복잡한 추천 알고리즘 대신 임박 재료 1개 중심 공공 API 검색
   - 입력 검증: 공백 제출 방지 및 유효 날짜 검증
   - 데이터 구조: 최소 필수 컬럼(6~7개) 중심 MariaDB 설계

2. YAGNI (You Aren’t Gonna Need It) - 보류할 예:
   - 복잡한 회원 권한 분리 및 소셜 멀티 로그인
   - 랭킹/배지/포인트 등 요구 없는 게임화 요소
   - 세부 알림 시간/음향 설정 및 영수증 OCR 카메라 스캔
   - 식재료 칼로리 DB 연동 및 유저 간 나눔 커뮤니티

위 내용을 바탕으로 구현 복잡도를 낮추고 기간 내 완성을 보장하기 위한 개발 유지/보류 원칙 지침을 출력해 줘.
```

## 🧪 3. MVP · AC 최종 정리 프롬프트

```markdown
[MVP 및 인수 조건(AC) 최종 정리 요청]

프로젝트 시연 및 단위 테스트 기준이 될 첫 핵심 사용자 흐름과 4가지 실행 상태별 인수 조건(AC) 명세서를 정리해 줘.

1. 첫 핵심 사용자 흐름 (Core Flow):
   [식재료 3초 입력] ➔ [D-Day 정렬 리스트 확인] ➔ [소진 완료 체크] ➔ [남은 항목 갱신 & 레시피/재구매 연동]

2. 4가지 실행 상태별 인수 조건 (Acceptance Criteria):
   - 정상 조건: 식재료 정상 등록 시 목록 추가 및 D-Day 자동 계산 여부
   - 잘못된 입력 조건: 공백 이름 제출 시 경고 메시지 출력 및 저장 거부 여부
   - 상태 변경 조건: '소진 완료' 체크 시 해당 항목만 활성 목록에서 제거되는지 여부
   - 빈 상태 조건: 식재료가 0개일 때 안내 문구(Empty View) 노출 여부

행동과 기대 결과, 시각적/데이터 검증 방법을 포함한 Markdown 표준 검증표 형태로 제공해 줘.
```
