- vehicle은 차량 ID, booking은 예약 ID, startsAt/endsAt는 UTC 기간, insuranceId는 선택 보험이다. 필요한 값은 이전 화면 선택으로 전달한다. 리소스 UUID를 문서의 예시 문자열로 대체하지 않는다.

2. 화면별 구현 흐름
1) 일일 요금은 version과 별도 저장하고, 가용 기간은 한국 시각 입력을 UTC로 바꿔 배열로 저장한다.
2) 서버는 1~24개 기간의 순서·겹침·종료를 검사한다. 차량 잠금 후 진행 예약을 포함하는지 확인하고 가용 기간을 교체한다.
3) 공개 요청은 세부 저장·주소·8장 사진·외관 등급·미래 가용 기간·차량 인증을 검사해 published로 바꾼다. 50에서 추천을 보고 적용할 수도 있다.

6. SOLID·KISS·YAGNI 적용 구분
- SOLID / 책임 분리(SRP): Availability 컴포넌트는 화면 입력과 표시를 담당하고 apps/api/src/modules/host/routes.ts는 해당 요청을 처리한다. UI에서 SQL을 실행하지 않고 필요한 검증·권한·상태 처리를 서버에 둔다.
- SOLID / 의존 방향: 결제 서비스는 PaymentProvider를 생성자로 받으며 개발·미설정 공급자를 구분한다. 이 화면이 외부 인증/분석을 호출할 때도 providers 경계를 사용한다. 공급자 호출이 없는 조회 화면에 불필요한 공급자 계층을 추가하지 않는다. 다섯 원칙의 공통 적용 설명은 ../04_SOLID_KISS_YAGNI.txt를 참조한다.
- KISS / 구현 단순화: Availability 컴포넌트에서 공통 api·Form·useData/Load를 필요한 곳에 재사용한다. 서버는 명시적 라우터와 SQL로 처리한다.
- YAGNI / 범위 제한: 이 화면의 현재 기능은 2절까지이며, 8절의 미연동·미구현 기능을 완료로 표시하지 않는다. 요구되지 않은 관리자·포인트·독립 마이크로서비스는 추가하지 않았다.
