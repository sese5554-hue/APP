2. 화면별 구현 흐름
1) booking 파라미터로 게스트 공개 평가를 조회하고 페이지 상태를 관리한다.
2) 서버가 해당 예약의 실제 호스트인지 먼저 확인한 뒤 닉네임·매너온도·완료 이용 수·평점 집계·미만료 인증 요약을 조회한다.
3) 후기는 작성자 닉네임·별점·내용을 10개 단위로 표시하며 예약 요청 상세 35로 돌아갈 수 있다. 휴대폰·면허 원문은 반환하지 않는다.

6. SOLID·KISS·YAGNI 적용 구분
- SOLID / 책임 분리(SRP): GuestProfile 컴포넌트는 화면 입력과 표시를 담당하고 apps/api/src/modules/host/routes.ts는 해당 요청을 처리한다. UI에서 SQL을 실행하지 않고 필요한 검증·권한·상태 처리를 서버에 둔다.
- SOLID / 의존 방향: 결제 서비스는 PaymentProvider를 생성자로 받으며 개발·미설정 공급자를 구분한다. 이 화면이 외부 인증/분석을 호출할 때도 providers 경계를 사용한다. 공급자 호출이 없는 조회 화면에 불필요한 공급자 계층을 추가하지 않는다. 다섯 원칙의 공통 적용 설명은 ../04_SOLID_KISS_YAGNI.txt를 참조한다.
- KISS / 구현 단순화: GuestProfile 컴포넌트에서 공통 api·Form·useData/Load를 필요한 곳에 재사용한다. 서버는 명시적 라우터와 SQL로 처리한다.
- YAGNI / 범위 제한: 이 화면의 현재 기능은 2절까지이며, 8절의 미연동·미구현 기능을 완료로 표시하지 않는다. 요구되지 않은 관리자·포인트·독립 마이크로서비스는 추가하지 않았다.
