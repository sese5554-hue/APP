2. 화면별 구현 흐름
1) phase=pickup으로 기존 점검을 조회하고 PhotoGrid에서 외관 8방향과 계기판 사진, 누적 주행거리를 받는다.
2) 사진은 purpose=inspection으로 먼저 업로드하고 업로드 ID를 제출한다. draft=true는 임시 저장이며 draft=false는 필수 사진을 모두 검사한다.
3) 예약자·CONFIRMED·시작 30분 전 조건을 잠금 확인하고 소유 사진·서로 다른 9장인지 검사한다. 최종 제출과 함께 IN_USE로 전환한다.

6. SOLID·KISS·YAGNI 적용 구분
- SOLID / 책임 분리(SRP): Inspection / InspectionForm 컴포넌트는 화면 입력과 표시를 담당하고 apps/api/src/modules/shared/inspections.ts는 해당 요청을 처리한다. UI에서 SQL을 실행하지 않고 필요한 검증·권한·상태 처리를 서버에 둔다.
- SOLID / 의존 방향: 결제 서비스는 PaymentProvider를 생성자로 받으며 개발·미설정 공급자를 구분한다. 이 화면이 외부 인증/분석을 호출할 때도 providers 경계를 사용한다. 공급자 호출이 없는 조회 화면에 불필요한 공급자 계층을 추가하지 않는다. 다섯 원칙의 공통 적용 설명은 ../04_SOLID_KISS_YAGNI.txt를 참조한다.
- KISS / 구현 단순화: 20·21은 phase만 다른 Inspection/InspectionForm과 PhotoGrid를 공유한다. 임시 저장과 제출은 같은 PUT API의 draft로 구분한다.
- YAGNI / 범위 제한: 이 화면의 현재 기능은 2절까지이며, 8절의 미연동·미구현 기능을 완료로 표시하지 않는다. 요구되지 않은 관리자·포인트·독립 마이크로서비스는 추가하지 않았다.
