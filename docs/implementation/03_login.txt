1. 화면 진입과 연결 구조
- apps/web/src/main.tsx의 App이 URL 화면 번호로 기능 모듈을 선택한다.
- 실제 화면 컴포넌트: AuthPage / Recovery (Auth.tsx).
- 컴포넌트 정의: apps/web/src/pages/Auth.tsx:16
- 컴포넌트 정의: apps/web/src/pages/Auth.tsx:449
- vehicle은 차량 ID, booking은 예약 ID, startsAt/endsAt는 UTC 기간, insuranceId는 선택 보험이다. 필요한 값은 이전 화면 선택으로 전달한다. 리소스 UUID를 문서의 예시 문자열로 대체하지 않는다.
- go는 기존 URL 검색값을 유지하고 전달된 null 키만 제거한다. 앱 시작 시 /api/auth/me로 사용자 세션을 복원한다.

2. 화면별 구현 흐름
1) 아이디·비밀번호 폼을 loginSchema로 검증하고 서버가 비밀번호 해시를 비교한다.
2) createSession은 난수 토큰의 해시를 DB에 저장하고 원본 토큰을 HttpOnly 쿠키로 전달한다. 웹은 반환 사용자를 저장하고 활성 역할의 홈으로 이동한다.
3) Recovery는 휴대폰 challenge를 인증한 뒤 아이디 조회 또는 비밀번호 재설정을 요청한다. 비밀번호 재설정은 기존 세션을 삭제한다.

6. SOLID·KISS·YAGNI 적용 구분
- SOLID / 책임 분리(SRP): AuthPage / Recovery 컴포넌트는 화면 입력과 표시를 담당하고 apps/api/src/modules/auth/routes.ts는 해당 요청을 처리한다. UI에서 SQL을 실행하지 않고 필요한 검증·권한·상태 처리를 서버에 둔다.
- SOLID / 의존 방향: 결제 서비스는 PaymentProvider를 생성자로 받으며 개발·미설정 공급자를 구분한다. 이 화면이 외부 인증/분석을 호출할 때도 providers 경계를 사용한다. 공급자 호출이 없는 조회 화면에 불필요한 공급자 계층을 추가하지 않는다. 다섯 원칙의 공통 적용 설명은 ../04_SOLID_KISS_YAGNI.txt를 참조한다.
- KISS / 구현 단순화: 약관·가입·로그인·인증을 AuthPage에서 화면 번호로 분기하고 공통 Form·Input·api를 재사용한다.
- YAGNI / 범위 제한: 이 화면의 현재 기능은 2절까지이며, 8절의 미연동·미구현 기능을 완료로 표시하지 않는다. 요구되지 않은 관리자·포인트·독립 마이크로서비스는 추가하지 않았다.

8. 현재 구현 범위와 한계
