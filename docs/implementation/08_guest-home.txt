2. 화면별 구현 흐름
1) 사용자의 닉네임·동네를 홈 문구에 반영하고 Search로 차량을 불러온다.
2) 지역 검색·전기차/SUV 칩·정렬·페이지 이동을 지원하고 검색 조건은 URL 검색 파라미터로 유지한다.
3) 서버는 공개·미삭제 차량만 조회하고 사진·평점 DTO로 변환한다. 차량 선택은 12, 지도 선택은 09로 이동한다.

6. SOLID·KISS·YAGNI 적용 구분
- SOLID / 책임 분리(SRP): Search 컴포넌트는 화면 입력과 표시를 담당하고 apps/api/src/modules/vehicles/routes.ts는 해당 요청을 처리한다. UI에서 SQL을 실행하지 않고 필요한 검증·권한·상태 처리를 서버에 둔다.
- SOLID / 의존 방향: 결제 서비스는 PaymentProvider를 생성자로 받으며 개발·미설정 공급자를 구분한다. 이 화면이 외부 인증/분석을 호출할 때도 providers 경계를 사용한다. 공급자 호출이 없는 조회 화면에 불필요한 공급자 계층을 추가하지 않는다. 다섯 원칙의 공통 적용 설명은 ../04_SOLID_KISS_YAGNI.txt를 참조한다.
- KISS / 구현 단순화: 홈·지도·검색결과·필터가 Search와 하나의 차량 목록 API를 공유한다. 필터를 URL에 표현해 별도 저장소 없이 화면 사이에 전달한다.
- YAGNI / 범위 제한: 이 화면의 현재 기능은 2절까지이며, 8절의 미연동·미구현 기능을 완료로 표시하지 않는다. 요구되지 않은 관리자·포인트·독립 마이크로서비스는 추가하지 않았다.
