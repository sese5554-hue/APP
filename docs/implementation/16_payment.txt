1. 화면 진입과 연결 구조
- apps/web/src/main.tsx의 App이 URL 화면 번호로 기능 모듈을 선택한다.
- 실제 화면 컴포넌트: Reservation (Guest.tsx).

- vehicle은 차량 ID, booking은 예약 ID, startsAt/endsAt는 UTC 기간, insuranceId는 선택 보험이다. 필요한 값은 이전 화면 선택으로 전달한다. 리소스 UUID를 문서의 예시 문자열로 대체하지 않는다.

2. 화면별 구현 흐름
1) 본인 결제수단을 불러오고 선택값이 없으면 기본 수단 또는 첫 수단을 사용한다. 새 수단 등록은 returnTo=16으로 46에 연결한다.
2) 폼은 기간·보험·수단·quoteTotal과 UUID Idempotency-Key를 보낸다. BookingService.create는 차량과 사용자 행을 잠그고 같은 키의 이전 요청을 먼저 확인한다.
3) 인증 3종의 유효성·본인 카드·자기 차량 여부·중복 일정·재계산 총액을 검사한 뒤 요금 스냅샷과 REQUESTED 상태를 저장한다. 반환 예약 ID로 17에 이동한다.

6. SOLID·KISS·YAGNI 적용 구분
- SOLID / 책임 분리(SRP): Reservation 컴포넌트는 화면 입력과 표시를 담당하고 apps/api/src/modules/bookings/routes.ts는 해당 요청을 처리한다. UI에서 SQL을 실행하지 않고 필요한 검증·권한·상태 처리를 서버에 둔다.
- SOLID / 의존 방향: 결제 서비스는 PaymentProvider를 생성자로 받으며 개발·미설정 공급자를 구분한다. 이 화면이 외부 인증/분석을 호출할 때도 providers 경계를 사용한다. 공급자 호출이 없는 조회 화면에 불필요한 공급자 계층을 추가하지 않는다. 다섯 원칙의 공통 적용 설명은 ../04_SOLID_KISS_YAGNI.txt를 참조한다.
- KISS / 구현 단순화: 14·15·16·48은 Reservation과 Quote를 공유하며 같은 기간·보험을 URL로 전달한다. 서버 견적을 재계산해 별도 견적 저장 테이블을 생략했다.
- YAGNI / 범위 제한: 이 화면의 현재 기능은 2절까지이며, 8절의 미연동·미구현 기능을 완료로 표시하지 않는다. 요구되지 않은 관리자·포인트·독립 마이크로서비스는 추가하지 않았다.
