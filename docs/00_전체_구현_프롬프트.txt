근차(geuncha) 전체 구현 마스터 프롬프트
문서 상태: 개발 지시문 / 앱 구현 전

당신은 이 저장소의 풀스택 개발자다. 원본 '앱 전체 기능 분류.txt', 'DB(마리아).txt', 00~51 SVG와 docs 문서를 읽고 차량 공유 앱을 구현하라. 단순 화면 시연으로 끝내지 말고 프론트엔드 입력 → API 검증 → MariaDB 저장 → 재조회까지 연결하라. 이번 지시문을 전달받아 실제 구현을 시작하면 필요한 코드를 작성하고 검증까지 수행하라.

1. 산출물과 범위
- Node.js + TypeScript 서버, TypeScript 프론트엔드, MariaDB를 사용한다. 모바일 우선 반응형 웹앱을 기본 대상으로 하며 네이티브 앱은 별도 요구가 있을 때만 추가한다.
- 화면 00부터 51까지 모두 구현한다. 화면 번호를 route 및 문서에서 추적할 수 있게 한다. SVG를 통째로 띄우는 방식으로 기능 구현을 대체하지 않는다.
- 앱 기능은 분류 문서가 기준이며 SVG는 화면 구성의 근거다. 49는 SVG를 근거로 차량 세부사항 저장 확인에 포함한다.
- 기능별 README를 docs/README_회원가입_로그인.txt, README_게스트.txt, README_공용.txt, README_호스트.txt로 분리한다. 루트 README.md에는 진입 안내, 실제 구현 순서, 실행법, 전체 상태를 기록한다.
- 최초 실행용 start.cmd와 start.sh를 제공하고, 개발·검증·운영 빌드 명령을 package.json에 정의한다.
- 지금 AWS 계정이나 서버에 접속하거나 배포하지 않는다. Ubuntu에서 실행 가능한 구성과 향후 배포 설명만 준비한다.

2. 시작 절차
- 저장소 지침, 기존 변경 내용, 실제 런타임과 도구를 먼저 확인한다. 사용자 원본과 기존 작업을 보존한다.
- docs/01_PRD.txt와 03_MariaDB_설계.txt를 읽고 데이터·권한·예약·결제 정책을 먼저 정한다.
- 구현에 착수할 때 채택할 라이브러리의 공식 문서와 호환 버전을 확인하고, 버전 및 사용 이유를 docs/06_사용도구.txt에 기록한다. 불필요한 패키지를 설치하지 않는다.
- 권장 초기 구성: apps/web(React + TypeScript), apps/api(Node.js + TypeScript), packages/contracts(요청·응답 스키마), database/migrations(SQL). 프론트엔드 도구와 서버 프레임워크는 실제 구현 시 결정하여 기록한다. MariaDB용 드라이버를 사용하며 다른 DB로 대체하지 않는다.
- 먼저 DB/API/테스트 기반을 만든다. 이후 화면 구현 이력은 00→51 순으로 남긴다. 뒤 번호 화면에서 쓰는 서비스나 DB는 선행 작성할 수 있으나 이력에서 명확하게 구분한다.

3. 화면별 작업 절차
- docs/pages의 해당 번호 TXT와 원본 SVG를 함께 읽는다.
- 화면의 역할·상태·입력 필드·이동 경로를 정의한다. loading, empty, error, validation, success를 구현한다.
- request/response 계약을 정하고 서버 검증, 역할 검사, 객체 소유권 검사를 작성한다.
- repository에서 매개변수 바인딩 SQL을 사용한다. 금액과 상태 전이를 서비스가 결정하게 한다.
- 프론트엔드를 실제 API에 연결하고 새로고침·직접 주소 진입·뒤로가기 시 상태 유실을 처리한다.
- 예약 충돌·중복 결제·타인 데이터 접근 등 핵심 위험에 필요한 테스트를 추가하고 실행한다. 단순 정적 문구 검증만으로 테스트를 대신하지 않는다.
- 각 단계의 소스 파일, 핵심 함수, 선택한 설계, 실행한 검증과 결과, 미완료 연동을 해당 README TXT와 구현기록에 적는다.

4. 지켜야 할 공통 규칙
- SOLID, KISS, YAGNI는 docs/04_SOLID_KISS_YAGNI.txt처럼 각각 구별하여 적용한다. 원칙 이름만 적고 불필요한 추상화를 늘리지 않는다.
- 인증 사용자를 요청 본문의 userId로 믿지 않는다. 서버 세션에서 식별한다. 모든 사용자별 API에서 소유권을 검사한다.
- 클라이언트의 금액, 외관 등급, 검증 성공, 예약 상태, 결제 성공을 신뢰하지 않는다.
- 카드번호·CVC·비밀번호·전체 면허번호·인증번호·외부 비밀값을 로그나 Git에 저장하지 않는다. 결제수단은 PG 참조값만 저장한다.
- 외부 공급자 계약·키가 없으면 개발용 adapter를 명시적으로 분리한다. 개발 성공을 실제 본인 확인·보험 가입·AI 분석·카드 결제·정산 지급으로 표시하지 않는다. 운영에서 개발 adapter를 활성화하면 서버 시작을 거부한다.
- 공급자 미설정 API는 명시적인 미설정 상태/503을 반환한다. 화면에서 실제 연동이 필요함을 표시하고 성공 상태로 진행시키지 않는다.
- 날짜는 UTC로 저장하고 Asia/Seoul로 표시한다. 돈은 원 단위 정수이며 반올림 규칙을 명시한다.
- 중복 예약 방지는 MariaDB 트랜잭션과 차량 행 잠금으로 보장한다. 프론트엔드 버튼 비활성화만으로 해결하지 않는다.
- 실시간 채팅은 예약 참여자만 허용하며 저장 후 전달한다. 업로드 접근 권한과 형식·크기를 서버에서 검사한다.

5. 완료 조건
- 52개 화면에 각 요구 기능이 있고 실제 API와 MariaDB에서 데이터가 유지된다.
- 회원가입/로그인, 차량 등록/검색, 예약 요청/승인/취소, 개발 결제, 인수/반납, 정산, 후기, 채팅, 문의 흐름을 재현할 수 있다.
- MariaDB 빈 DB부터 migration과 개발 seed를 적용할 수 있으며 재실행으로 데이터를 잃지 않는다.
- 최초 실행 파일과 개발 명령이 동작하고 build/typecheck 및 핵심 통합 테스트가 통과한다.
- README 및 기능별 TXT에 실제 검증 증거를 기록한다. 실행하지 못한 검증은 사유와 함께 '미검증'으로 남긴다.
- 최종 응답에서 구현 완료 범위, 실행 방법, 테스트 결과, 미연동 항목을 분리한다. 사용자에게 Git push 요청이 있으면 원격과 브랜치를 확인하고 해당 변경을 커밋·push한다. 강제 push는 하지 않는다.
